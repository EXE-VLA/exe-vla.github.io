EXE: Egocentric Cross‑Embodiment Pretraining via Factorized Latent Actions for VLA Models

Not every part of an action is worth sharing across embodiments. We split the action, share only the part that transfers, and let language decide what counts as the same skill.

Authors
Qingyuan Cai, Bo Zhang, Yongzhen Huang, Jianyu Chen
Benchmarks
RoboTwin 2.0 · RoboCasa GR1 · AgileX Piper (real)
Egocentric human video → factorized latent actions → robot policy
Egocentric human video Shared positional codebook Gripper & dexterous-hand policies

Vision-Language-Action models are limited less by architecture than by data. Collecting robot demonstrations means physical teleoperation on real hardware — expensive, slow, and narrow in the range of scenes and tasks it can cover. Egocentric human video is the opposite: thousands of hours of first-person manipulation already exist, with diverse objects, natural language, and a camera viewpoint that happens to match a robot's wrist or head camera almost exactly.

The obstacle is that a robot cannot imitate a hand. Human motion is parameterized by finger joints; robot motion by end-effector poses with a gripper or a dexterous hand. Prior work bridges this gap in one of two ways, and each has a structural cost. If you force the entire action into a single shared codebook, the shared codes end up absorbing embodiment-specific geometry, which buries the task semantics you actually wanted. If you instead learn latent actions from raw visual frame transitions, the action signal gets entangled with background and lighting, and the latents end up encoding visual noise rather than manipulation skill.

We think both failures come from the same unexamined assumption: that an action is a single, indivisible thing that either transfers or does not. It is not.

# Which parts of an action actually transfer?

Consider what a human hand and a parallel gripper genuinely have in common. Both must move to a location in space. Reaching toward a cup, following a trajectory over a table, approaching a target — that spatial intent is expressed as a 3D position of the wrist or end-effector, and it means the same thing regardless of what is attached to the end of the arm.

Now consider what they do not share. Finger joint angles, wrist rotation conventions, gripper open/close geometry: these are properties of the hardware. A five-fingered MANO configuration has no counterpart in a two-jaw gripper, and pretending otherwise only injects noise.

So rather than unifying the whole action, we factorize it. Each action vector is split by a static routing table into a shared group — the 3D wrist or end-effector position, expressed in the egocentric camera frame — and a specific group holding everything embodiment-dependent. The shared group is quantized by one codebook trained jointly on human and robot data. The specific group gets a private codebook per domain. Residual quantization operates within each group, so the shared codebook never sees an embodiment-specific dimension.

Feature group-routed action tokenizer
Human actions (102-D: MANO wrist and finger joints) and robot actions (20-D: end-effector pose and gripper) are each split by the routing table. The 3D wrist / end-effector position goes to the shared codebook, updated from both domains. Rotation, gripper state and finger joints go to per-domain specific codebooks. Both positional signals live in the egocentric camera frame, so they are geometrically comparable in the first place.

# The method, in three stages

With the factorization fixed, the rest of EXE is a three-stage recipe. Stage 1 trains the factorized tokenizer and freezes it. Stage 2 co-trains a VLM backbone on human and robot data to reshape its representations. Stage 3 fine-tunes an action expert for continuous control. We walk through them in order.

Stage 1 — Training Factorized Action Tokenizer

Having a shared subspace is not the same as having an aligned one. The obvious tool is contrastive learning: pull together human and robot latents that land on the same shared code, push apart those that do not. We do exactly that with a symmetric InfoNCE term, and it helps — it stabilizes the shared codebook and makes code semantics consistent across domains.

But there is a bootstrapping problem hiding in it. Code assignment is determined by spatial trajectory. So if a human and a robot perform the same task along different trajectories, they get routed to different codes — and therefore never become contrastive positives. The pairs most worth aligning are exactly the pairs the objective cannot see.

A concrete case. A human grasps a cup from above with five fingers. A robot clamps the same cup from the side with a parallel gripper. Both are executing “grasp the cup.” Their spatial trajectories differ substantially, so a purely geometric objective would push them apart — the opposite of what a cross-embodiment representation should do.

Semantic equivalence is not recoverable from geometry, so we bring in a signal that is invariant to embodiment: language. A frozen Qwen3-Embedding-8B encodes each sample's task instruction offline. We then build two cross-domain similarity matrices — one over text embeddings, one over shared action latents — and distill the former into the latter:

ℒlang = ‖ Sact − Stext ‖F2

The text matrix is detached and acts purely as a soft target. We compute the loss only over cross-domain pairs, since within a domain the text similarity degenerates to 1. Importantly, language never enters the encoder input — it shapes the distribution of the shared latent space during tokenizer training and is then discarded. Nothing at deployment depends on it.

Stage 2 — Cross-Embodiment VLM Pretraining

The tokenizer gives us a vocabulary; the remaining question is how a VLA absorbs it. Stage 2 co-trains a Florence-2-large backbone on egocentric human video and robot demonstrations, alternating between domains: on human steps the model predicts only shared codes, on robot steps it predicts shared and robot-specific codes. No action expert is involved — this stage exists only to reshape the backbone's internal representations.

Stage 3 — VLA Fine-tuning

Stage 3 drops discrete supervision entirely and trains an action transformer to regress continuous actions on downstream robot data. To make sure the Stage 2 knowledge is actually reused rather than quietly forgotten, we extract the backbone's hidden states at the action-placeholder positions as Bridge Features and concatenate them into the conditioning context. At inference there is no tokenizer, no codebook, and no language model: the discrete vocabulary was a training-time device all along.

Stage 2 co-training and Stage 3 fine-tuning
Placeholder tokens are appended to the prompt and the LM head predicts a shared code at each position. In Stage 3 the hidden states at those same positions become Bridge Features for the action expert, which decodes continuous actions from noise.

# Does the shared codebook actually share?

A design can be well-motivated and still not do what it claims, so before looking at success rates we checked the latent space directly. We pushed real human and robot actions through the trained tokenizer and ran a joint t-SNE on the quantized codebook vectors.

The shared space behaves as intended: human and robot tokens overlap in compact clusters, and tokens carrying the same code id form local groups. The specific space behaves as intended in the opposite way — the two domains separate cleanly, because their codebooks were trained independently and encode domain-private quantities.

Cluster overlap alone is a weak claim, though. To check that a shared code means something physical, we picked a code activated by both the human and the robot inside a single episode and plotted the corresponding trajectory segments. Both trace a top-to-bottom placing motion that lowers the end-effector to set an object down. One code, one spatial intent, two embodiments.

# Does it help the robot?

To isolate what the pretraining buys us, we compare against EXEbase: the same framework and the same Florence-2-large backbone, with the action expert trained directly on downstream robot data. No Stage 1, no Stage 2, and deliberately no large-scale teleoperated robot pretraining either. Any gap between the two is attributable to egocentric human video passing through our factorized representation.

The same pretraining has to work across embodiments that do not share a kinematic structure, so we test on a bimanual parallel gripper (RoboTwin 2.0, 50 tasks), a dexterous-hand humanoid (RoboCasa GR1, 24 tasks), and a real AgileX Piper platform.

The gains hold across all four settings, and they are largest exactly where they should be. On RoboTwin's hard split — randomized backgrounds, lighting and object layouts — the baseline drops from 68.4% to 65.2%, while EXE actually goes up, from 75.6% to 76.8%. Pretraining on diverse human video appears to buy robustness to visual variation, not just raw task competence.

Against published baselines, EXE reaches 76.2% average. That is ahead of SmolVLA and TurboVLA, and also ahead of X-VLA — which is the comparison we find most informative, because X-VLA benefits from large-scale teleoperated robot pretraining that we deliberately excluded. Human video, routed through a factorized action space, substitutes for a substantial amount of robot data.

# On a real robot

Simulation results can reward the wrong things, so we ran the same recipe on an AgileX Piper bimanual platform. We collected 2,450 teleoperated demonstrations of “sweep the rubbish,” fine-tuned Stage 3 from the Stage 2 checkpoint, and evaluated 10 rollouts per condition.

In-distribution, EXE reaches 80% against the baseline's 60%. The improvement concentrates on visually colorful objects — a broom-and-dustpan set with distinctly colored parts, for instance — which fits the idea that egocentric pretraining teaches the policy to exploit color cues it would otherwise ignore. With unseen objects added as distractors, both policies degrade sharply, but EXE degrades less: 30% against 10%. Neither number is deployable, and we would rather report that plainly than round it into a success story.

# What each piece contributes

Three components could each plausibly be doing nothing, so we removed them one at a time.

InfoNCE contributes a modest but consistent gain by stabilizing the shared codebook. Language-guided distillation adds more, and it adds it in the regime we predicted — where trajectories differ enough that InfoNCE has no positive pairs to work with. The Bridge feature gives the largest single jump, which is a useful negative result about the rest of the pipeline: shaping the backbone in Stage 2 is not sufficient on its own, you also have to give Stage 3 an explicit path back to those representations.

Mixing ratio, and whether any of this depends on EgoLive

Two more things worth knowing. First, the human-to-robot ratio in Stage 2 co-training matters, and the balanced 1:1 mixture wins — over-weighting robot data biases the backbone back toward the robot domain and erodes the shared representation we just paid to build. Second, the method is not an artifact of one dataset: swapping EgoLive for VITRA-1M or EgoDex still beats the no-pretraining baseline by a wide margin.
